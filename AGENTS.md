# AGENTS.md

## Commands that matter

- Run Make targets from the repo root; they encode the required `cd`, venv, env-file, and compose-file details.
- Setup/CI order is `make deps && make check-formatting && make lint`. CI only runs those commands on Python 3.10.12; no tests, typecheck, or build run in CI.
- `make deps` creates separate virtualenvs in `backend/.venv` and `frontend/.venv`; dependencies come from separate `requirements.txt` files and there are no lockfiles.
- Dev flow: `make create-data`, `make run-dev-db`, then `make run-dev-backend` on port 11014 and `make run-dev-frontend` on port 11013. `make run-dev-db` starts MySQL, sleeps 10 seconds, then runs Alembic with `ENV_FILE=.dev.env`.
- Formatting is `make format`; check-only formatting is `make check-formatting` using Black, isort, and djlint with `--profile=jinja`. Lint is `make lint` using flake8 with different ignore sets for backend/frontend.
- Backend migrations only: use `make autogen-migration message='...'`, `make migrate-dev`, or `make downgrade-dev`. Review autogenerated Alembic revisions before keeping them.

## Architecture and data boundaries

- This is two FastAPI apps plus MySQL/nginx, not a JS-build frontend. Backend entrypoint is `backend.server:app`; frontend entrypoint is `frontend.main:app` and renders Jinja templates from `frontend/frontend/templates` with static files from `frontend/frontend/static`.
- Backend owns the schema and Alembic metadata (`backend/backend/models.py`). Frontend keeps a duplicate, older SQLAlchemy model set for direct MySQL reads/writes; if shared tables change, update backend models, frontend models, and an Alembic migration together.
- `ENV_FILE` is loaded at import time in backend, frontend, and Alembic; set it before importing app modules or running one-off scripts because SQLAlchemy engines are module-level.
- Runtime data is under `DATA_FOLDER`: `subscription_manager`, `videos/`, and `thumbnails/`. `make create-data` seeds this from the repo-root `subscription_manager` file.
- Nginx proxies `/` to the frontend and serves `/videos` and `/thumbnails` directly from mounted `/data`. Production compose files contain server-specific host paths; check them before running prod targets.
- Backend startup starts APScheduler and the download service; frontend routes such as `/refresh_rss` and `/ready_up_server` trigger backend side effects.

## Gotchas

- Do not invent a pytest/unittest command: no test runner, test config, or test files are present.
- `docker-compose.prod_vpn.yml` is ignored and absent in a clean checkout; avoid `prod_vpn` Make targets unless that file is supplied externally.
- Some README details are stale; trust executable sources first. Current retention thresholds live in `backend/backend/constants.py`, and playlist code exists despite the README saying it is future work.
- Fresh migrations can need `DATA_FOLDER/subscription_manager` and network access because the channel backfill migration reads the OPML file and fetches YouTube RSS data.
- `make first` is not a verification target; it downloads a fallback mp4 and moves it to an old `frontend/static` path.
